## v0 architecture

v0 builds three small modules in the core and one file in the Node adapter, placed so that later versions only add files and never move them.

&#91;embedded content: v0 architecture · modules and the compiler-enforced boundary\]

Anything that touches the disk lives above the line. The core below it only ever sees bytes and numbers, which is what lets the same code run in a browser in v10.

**v0 public API** (contracts only; you write the bodies)

```ts
// packages/core/src: pure TypeScript
export interface VectorSet { readonly dim: number; readonly count: number; readonly data: Float32Array }
export interface IdSet { readonly dim: number; readonly count: number; readonly data: Int32Array }
export function parseFvecs(bytes: ArrayBuffer | Uint8Array): VectorSet;
export function parseIvecs(bytes: ArrayBuffer | Uint8Array): IdSet;
export function encodeFvecs(set: VectorSet): Uint8Array;
export function encodeIvecs(set: IdSet): Uint8Array;
export function vectorAt(set: VectorSet, i: number): Float32Array;

export type Metric = 'l2' | 'ip' | 'cosine';
export type DistanceFn = (a: Float32Array, aOff: number, b: Float32Array, bOff: number, dim: number) => number;
export const l2Squared: DistanceFn;
export const negInnerProduct: DistanceFn;
export const cosineDistance: DistanceFn;
export function getDistanceFn(metric: Metric): DistanceFn;
export function distance(metric: Metric, a: Float32Array, b: Float32Array): number;
export function normalizeInPlace(data: Float32Array, off: number, dim: number): void;

export class VMaxError extends Error {}
export class DatasetFormatError extends VMaxError {}
export class DimensionMismatchError extends VMaxError {}
export class ZeroVectorError extends VMaxError {}

// packages/core/src/adapters/node: Node only
export function readFvecs(path: string): Promise<VectorSet>;
export function readIvecs(path: string): Promise<IdSet>;
```

**Key design decisions**

| Decision | Choice | Why | Rejected alternative |
| --- | --- | --- | --- |
| Data layout | one flat `Float32Array` per set | one allocation, cache-friendly, and the same layout the index uses in v5 | an array of arrays: thousands of small objects and slow garbage collection |
| Hot-path signature | array + offset + dim | zero allocations per distance call | passing `subarray()` views |
| Distance rule | smaller always means closer | search code never needs to know the metric | "higher is better" for inner product and cosine, which means two code paths |
| Byte parsing | `DataView`, little-endian | explicit byte order, no alignment rules | a `Float32Array` view: faster, but depends on alignment and machine byte order |
| Validation | at the boundaries (parser, safe wrapper) | hot loops stay fast | checks inside every distance call |
| Errors | a small class hierarchy | callers can catch errors by type | plain `Error` with message strings |

## Day 1: Repo foundations and the portability boundary

**Objective.** By tonight, lint, type-check and tests pass locally and on GitHub, the core is walled off from Node and browser APIs, and your machine can build native addons.

**Concepts (why before how)**

- **Monorepo with npm workspaces:** the core, API, web app and tools live in one repo with one install, but stay separate packages with separate rules.
- **Type-check is not the test run:** Vitest strips TypeScript types without checking them, so code with a type error can still pass its tests. That's why CI runs `tsc` as its own step.
- **The portability boundary:** the core's tsconfig uses `"lib": ["ES2022"]` (no DOM) and `"types": []` (no automatic `@types/node`). Inside the core, `fs`, `window`, `process`, `console` and `setTimeout` simply don't exist for the compiler. Node-side code (adapters, tests, tools) gets a separate tsconfig with Node types.
- **Why the C++ toolchain today:** hnswlib-node is needed in v4. A broken compiler found on Day 19 costs a day; found today, it costs an hour.

**Design: what Day 1 creates**

**Settings that matter, and why**

| Setting | Value | Why |
| --- | --- | --- |

| core `types` | `[]` | no `@types/node`, so no `fs`, `process` or `Buffer` |

## Day 2: Reading .fvecs and .ivecs files

**Objective.** Turn the raw SIFT files into a flat, validated dataset in memory, and prove it with tests that include broken files.

**Concepts**

- **The format.** Each record is a 4-byte little-endian integer `d`, followed by `d` values: 32-bit floats in `.fvecs`, 32-bit integers in `.ivecs`. So each record is `4 + 4d` bytes, and the file is just records back to back with no header ([TEXMEX](http://corpus-texmex.irisa.fr/)).
- **Ground truth.** In the `_groundtruth.ivecs` file, record *i* lists the 0-based IDs of query *i*'s 100 nearest base vectors, closest first. In v1 this becomes your answer key.
- **Endianness.** Little-endian means the least significant byte comes first. `DataView` lets you state the byte order explicitly; typed arrays use your machine's order, which is little-endian on practically every machine you'll use.
- **Shared memory pools.** A Node `Buffer` is often a window into a larger shared block, so `buf.buffer` can contain other data before and after your file. Always carry `byteOffset` and `byteLength` along.
- **Alignment.** A `Float32Array` view must start at a byte offset that's a multiple of 4, or the constructor throws a `RangeError`.
- **Flat layout.** All vectors go in one `Float32Array` of length `count × dim`, row by row: vector *i* starts at index `i × dim`. One allocation, no per-vector objects, and the same layout the index uses in v5.

**Design: the API (contracts only; the bodies are yours)**

```ts
// packages/core/src/dataset.ts (pure: no Node, no DOM)
export interface VectorSet {
  readonly dim: number;
  readonly count: number;
  readonly data: Float32Array; // count * dim values, row by row
}
export interface IdSet {
  readonly dim: number;
  readonly count: number;
  readonly data: Int32Array;
}
export function parseFvecs(bytes: ArrayBuffer | Uint8Array): VectorSet;
export function parseIvecs(bytes: ArrayBuffer | Uint8Array): IdSet;
export function encodeFvecs(set: VectorSet): Uint8Array;
export function encodeIvecs(set: IdSet): Uint8Array;
export function vectorAt(set: VectorSet, i: number): Float32Array; // a view; for convenience, never in hot loops

// packages/core/src/adapters/node/files.ts (Node only)
export function readFvecs(path: string): Promise<VectorSet>;
export function readIvecs(path: string): Promise<IdSet>;
```

Accepting a `Uint8Array` lets the Node adapter pass a `Buffer` straight in (a `Buffer` is a `Uint8Array`), offsets and all. The `encode` functions earn their place twice: tests build small files with them today, and in v4 you'll write subset datasets with your own ground truth.

**Decisions you make today** (record each in a code comment)

1. **DataView or a Float32Array view?** DataView reads each value with explicit little-endian order and has no alignment rules, but it's slower. A view is fast but depends on alignment and machine byte order. Recommendation: DataView now; measure parse time on SIFT1M in v4 and optimise only if it matters.
2. **Empty file: error or empty dataset?** Recommendation: error, because an empty dataset file is almost always a failed download.
3. **NaN or Infinity in a vector:** reject it, naming the record. Base data must be finite or every distance becomes NaN.
4. **Maximum dimension:** pick a sanity cap such as 65,536, so a corrupt first integer can't make you allocate gigabytes.

**Failure cases: decide the behaviour before coding**

| Input | Expected behaviour |
| --- | --- |
| Empty file | `DatasetFormatError`: empty file |
| Fewer than 4 bytes | error: truncated header |
| `d` ≤ 0, or above the cap | error naming the bad value |
| A later record's `d` differs from the first | error naming the record number |
| Last record cut short | error: truncated record, with expected and actual byte counts |
| NaN or Infinity value | error naming the record and position |
| A `Uint8Array` with a non-zero `byteOffset` | parses correctly; test this on purpose |
| An `.ivecs` file passed to `parseFvecs` | can't always be detected, because the integers read as tiny meaningless floats. Note it in a comment: validation checks structure, not meaning |

## Day 3: Distance functions

**Objective.** Three distance functions that follow one rule (smaller means closer), tested against hand-computed values and properties, plus your first speed number.

**Concepts**

```latex
d_{L2}(a,b) = \sum_{i=1}^{d} (a_i - b_i)^2 \qquad d_{IP}(a,b) = -\sum_{i=1}^{d} a_i b_i \qquad d_{\cos}(a,b) = 1 - \frac{a \cdot b}{\lVert a \rVert \, \lVert b \rVert}
```

- **Squared L2.** The sum of squared differences. Skipping the square root keeps the same ranking, because the square root only ever grows, and it saves time.
- **Inner product as a distance.** A bigger dot product means more similar, so the distance is its negative: smaller is closer, like the others.
- **Cosine distance.** 0 for the same direction, 1 for perpendicular, 2 for opposite.
- **The unit-vector identity.** For vectors of length 1, the squared L2 distance equals 2 − 2 × (a · b). So after normalising, L2 and cosine rank results identically. That's why we'll store normalised vectors when the metric is cosine.
- **Float precision.** A `Float32Array` rounds every stored value to 32 bits (like `Math.fround`), but JavaScript arithmetic runs in 64 bits. Results differ slightly from C++ float code, so tests compare with a tolerance, never exact equality.
- **A silent JavaScript trap.** Reading past the end of a typed array returns `undefined`, and arithmetic on `undefined` gives `NaN`, with no exception. The fast functions don't check bounds, so the safe wrapper must.
- **No allocations in hot loops.** `subarray()` creates a new object on every call. The fast functions take the whole flat array plus an offset, so scanning a million vectors allocates nothing.

**Design: the API**

```ts
// packages/core/src/distance.ts
export type Metric = 'l2' | 'ip' | 'cosine';

// Fast path: no checks, no allocations. The caller guarantees valid offsets and dim.
export type DistanceFn = (a: Float32Array, aOff: number, b: Float32Array, bOff: number, dim: number) => number;
export const l2Squared: DistanceFn;
export const negInnerProduct: DistanceFn;
export const cosineDistance: DistanceFn; // reference version: computes both norms on every call
export function getDistanceFn(metric: Metric): DistanceFn;

// Safe path: validates first; throws DimensionMismatchError or ZeroVectorError.
export function distance(metric: Metric, a: Float32Array, b: Float32Array): number;

export function normalizeInPlace(data: Float32Array, off: number, dim: number): void;
```

**Decisions**

1. Bounds checks live only in the safe wrapper and at API boundaries, never in the hot loop. Document "the caller guarantees" on every fast function.
2. A zero vector under the cosine metric throws `ZeroVectorError` in the safe path instead of returning NaN.
3. Accumulate in a plain JavaScript number. No speed tricks (loop unrolling, several accumulators) until v5, and only with a benchmark to prove them.

**Failure cases**

| Case | Expected behaviour |
| --- | --- |
| `a` and `b` have different lengths (safe path) | `DimensionMismatchError` |
| Offset past the end (fast path) | silently returns NaN: this is why the safe path exists; test that the safe path catches it |
| Zero vector with cosine | `ZeroVectorError` |
| NaN inside a vector | result is NaN; the dataset loader already rejects these |
| Identical vectors | exactly 0 for squared L2; cosine within a small tolerance of 0 |

**Tests**

Hand-computed:

- `l2Squared` of \[1, 2\] and \[4, 6\] is 25.
- `negInnerProduct` of \[1, 2\] and \[3, 4\] is −11.
- `cosineDistance`: \[1, 0\] vs \[0, 1\] is 1; \[1, 1\] vs \[2, 2\] is about 0; \[1, 0\] vs \[−1, 0\] is 2.
- The same cases at non-zero offsets inside a larger flat array, to catch off-by-one offset bugs.

Property tests with fast-check (random finite vectors):

- Symmetry: d(a, b) equals d(b, a) for all three metrics.
- Squared L2 is never negative, and d(a, a) is 0.
- After normalising both vectors, squared L2 is within tolerance of 2 − 2 × (a · b).
- Cosine distance stays between 0 and 2, within tolerance.
